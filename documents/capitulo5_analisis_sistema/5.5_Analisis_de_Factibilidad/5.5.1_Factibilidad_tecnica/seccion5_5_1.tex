Para determinar la factibilidad técnica es necesario evaluar los aspectos tecnológicos del proyecto para averiguar si es posible desarrollar el nuevo sistema teniendo en cuenta los recursos técnicos actuales \cite{kendall_analisis}. De esta manera y debido a las características propias del prototipo, se evalúa únicamente el software necesario para conseguir una plataforma para desarrollar la aplicación móvil, el sistema para almacenar la base de datos con soporte para análisis geoespacial, y el equipo de hardware requerido.

\subsubsection{Software y Servicios Externos}

\label{subsubsec: software}
Primero, para el desarrollo del prototipo móvil es necesario la utilización de un \textbf{marco de trabajo} que nos permita realizar aplicaciones móviles para Android. Se determinó que \textbf{Flutter} es la tecnología principal a utilizar, basándose primordialmente en que es la herramienta que el equipo domina, mitigando la curva de aprendizaje y los riesgos asociados en tiempo y costo operativo.

Aunado a este dominio técnico por parte del equipo, \textbf{Flutter ofrece un entorno óptimo} para la construcción de un producto mínimo viable (MVP) por ventajas como su renderizado a nivel de píxel, su repositorio oficial de paquetes centralizado y su naturaleza multiplataforma\cite{flutter_businessvalue}. Si bien el desarrollo del presente proyecto se enfoca únicamente en Android, el uso de esta tecnología garantiza que, como parte del trabajo a futuro, el proyecto pueda retomarse y expandirse a otros sistemas operativos de manera sencilla, manteniendo la interfaz diseñada y reutilizando aproximadamente el 90\% del código escrito \cite{suri2022cross}. Segundo, una vez definida la herramienta para el prototipo móvil, lo siguiente por analizar es el \textbf{sistema gestor de bases de datos}. Este almacenará la red vial de la alcaldía Gustavo A. Madero, los datos de los usuarios y el modelo integrado con las ponderaciones de criminología ambiental. Debido a que se requiere soporte nativo para bases de datos espaciales, integraciones robustas de seguridad y alta disponibilidad, se opta por \textbf{Supabase}.

A pesar del gran número de herramientas \textit{open-source} autohosteadas que existen en el mercado (como Appwrite o Convex), al no contar con la infraestructura de hardware propia ni el tiempo necesario para la configuración de microservicios, se determina que la adopción de un \textit{Backend as a Service} (BaaS) es la ruta más factible, ya que facilita la implementación, asegura disponibilidades altas, ofrece tiempos de respuesta óptimos y provee herramientas en tiempo real.

A nivel técnico y operativo, se seleccionó esta plataforma porque el equipo de desarrollo ya cuenta con experiencia previa en su manejo, lo que elimina la curva de aprendizaje y reduce significativamente los riesgos de retraso. Además, de manera nativa, Supabase ofrece las herramientas necesarias para la gestión de bases de datos geoespaciales y tambien permite integrar un motor de ruteo en grafos mediante una simple extensión (pgRouting). Esto elimina la necesidad de desarrollar un motor externo y, a corto plazo, permite integrar de manera más rápida la lógica de rutas con la aplicación móvil. Tercero, aunque Supabase y Flutter cubren por sí mismos la mayor parte de las funcionalidades del sistema, existen \textbf{cuatro que dependen por parcial o completamente de proveedores externos}: (1) el envío de correos electrónicos, (2) los mapas base, (3) la búsqueda de lugares (geocodificación) y (4) el envío de notificaciones \textit{push} cuando la aplicación no está abierta en el dispositivo. Para elegir el proveedor de cada uno de estos servicios se definieron los siguientes criterios de selección:
\begin{enumerate}
    \item Costo y disponibilidad de un plan gratuito.
    \item Facilidad de integración.
    \item Compatibilidad con las tecnologías ya seleccionadas (Flutter y Supabase).
    \item Cobertura de las funcionalidades que exigen los requerimientos del sistema.
\end{enumerate}

% --- Envío de correos ---
En el caso del \textbf{correo electrónico}, el sistema solo lo utiliza para enviar el correo de verificación de la cuenta. Aunque Supabase Auth incluye un servidor SMTP propio, este solo entrega correos a los miembros del equipo del proyecto, con un límite de dos correos por hora y sin garantía de servicio \cite{supabase_smtp}, por lo que es necesario configurar un proveedor externo. 

Resend ofrece una cuota gratuita suficiente para el volumen del prototipo y es el único con una integración oficial que configura Supabase Auth de forma automática. Su única condición es contar con un dominio propio verificado. Por ello, se selecciona \textbf{Resend} como proveedor SMTP. La tabla \ref{tab:comparativa-correo} muestra sus características.

% --- Búsqueda de lugares ---
En la \textbf{búsqueda de lugares}, la licencia resulta más determinante que el precio. Se selecciona \textbf{Geoapify}, consultado desde una Edge Function de Supabase que resguarda la llave de acceso y acota los resultados al área de servicio. 

Antes de utilizar este servicio, la búsqueda consulta un índice propio en PostGIS con los lugares y calles de OSM del área de servicio, que responde sin costo y sin enviar datos a terceros. Este flujo cumple rigurosamente con la regla de negocio \textbf{RN-16}, ya que la búsqueda se orienta con el área de servicio y no con la posición del usuario, protegiendo su privacidad. % --- Notificaciones push ---
Por último, las \textbf{notificaciones \textit{push}} se utilizan para las alertas de reportes y de seguimiento cuando la aplicación no está abierta. Las alertas que se generan en el propio dispositivo, como entrar a una zona de riesgo durante la navegación, y la ubicación en vivo con la aplicación abierta no requieren este servicio, ya que se resuelven con notificaciones locales y con Supabase Realtime \cite{supabase_pricing}. \textbf{FCM} es la única opción sin límite de usuarios en su plan gratuito, cuenta con un paquete oficial y con una guía de Supabase que describe el flujo completo de envío. Por ello, se selecciona FCM, con envíos desde una Edge Function de Supabase. Su uso tiene dos condiciones: el dispositivo debe contar con Google Play Services y, a partir de Android 13, la aplicación debe solicitar el permiso de notificaciones en tiempo de ejecución \cite{firebase_messaging}. No obstante, su implementación queda reservada como contingencia debido a que su plan gratuito restringe el servicio a un máximo de 1,000 usuarios activos al mes (requiriendo un plan de pago de \$19.00 USD mensuales al superar dicha cuota) \cite{onesignal_pricing}, y a que su arquitectura técnica opera fundamentalmente como una capa adicional sobre la propia infraestructura de FCM \cite{onesignal_flutter}.


\subsubsection{Hardware}

Con la elección de tecnologías de la sección \ref{subsubsec: software}, podemos determinar que Supabase no requiere condiciones de hardware específicas, dado que su infraestructura no se alojará en un equipo propio, sino que opera directamente como un servicio en la nube (\textit{BaaS}). Por otro lado, para el desarrollo de la interfaz y la lógica de Flutter se eligió el editor Visual Studio Code, el cual es ligero y no demanda especificaciones excepcionales. Sin embargo, para compilar y probar la aplicación móvil en Android se requiere el SDK provisto por Android Studio, lo que condiciona la infraestructura necesaria.

Para el desarrollo del prototipo, si las pruebas se hacen exclusivamente mediante conexión a un dispositivo físico, se necesitan aproximadamente 8 GB de memoria RAM y 8 GB de espacio libre en disco para ejecutar el entorno. Si, por el contrario, se utiliza el emulador de Android, los requisitos recomendados suben a 16 GB de RAM y 16 GB de espacio libre, con una resolución de pantalla mínima de 1280 $\times$ 800 píxeles \cite{androidstudio_install}.

Para cubrir de forma holgada las tareas de programación, compilación del código en Dart y pruebas de rendimiento durante el ciclo de 10 meses, el equipo de trabajo empleará la siguiente infraestructura física, la cual satisface los requisitos de memoria y procesamiento:
\begin{itemize}
    \item \textbf{Equipos de cómputo:} Tres laptops de gama media para desarrollo (con procesadores equivalentes a Intel Core i5 / Ryzen 5, 16 GB de RAM y almacenamiento SSD), conformadas específicamente por una Lenovo IdeaPad Flex 5 Gen 8 (AMD) \cite{lenovo_flex5}, una Lenovo IdeaPad Slim 3i (Intel) \cite{lenovo_slim3i} y una ASUS Vivobook 14 (X1404) \cite{asus_vivobook}.
    \item \textbf{Dispositivo de pruebas físicas:} Un equipo inteligente Honor Magic6 Lite 5G \cite{telcel_honor} provisto con sistema operativo Android, el cual se destinará a las pruebas de rendimiento en vivo y la validación de hardware nativo, como los sensores de geolocalización (GPS).
\end{itemize}

\subsubsection{Personal y capacidades técnicas}
Las capacidades técnicas requeridas se concentran en dos herramientas. Por un lado, Supabase expone métodos simples para interactuar con la base de datos, ya que la aplicación consulta la lógica de rutas mediante funciones remotas (RPC) \cite{supabase_arquitectura}, por lo que su curva de aprendizaje es baja y no requiere administrar infraestructura propia. Por el otro, el mayor reto técnico del proyecto es el lenguaje Dart y el marco Flutter, con los que se construye la interfaz y la lógica del cliente \cite{supabase_flutter}.

Por esta razón, aunque los integrantes del equipo cuentan con bases sólidas de programación, se asume una curva de aprendizaje continua orientada a dominar especificidades de Dart y Flutter. Como se establece en la matriz de riesgos del proyecto (R-23), esta situación técnica se mitiga asignando recursos para capacitación continua, apoyándose en la documentación oficial y adoptando un enfoque incremental de prototipos en la etapa de programación. Esto permite validar funcionalidades en ciclos cortos y ajustar el alcance de cada iteración conforme el equipo afianza su dominio técnico.
